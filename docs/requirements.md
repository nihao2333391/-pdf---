## 1. 产品目标与首版范围

用户在微信小程序中整理一次报销的材料，最终得到：

- 一份按费用组排序的报销凭证 PDF。
- 一份说明各组内容及对应 PDF 页码的 Word 文件。
- 一条可以重新编辑、再次生成和导出的本机历史记录。

首版采用手机本地处理、本机保存的方向。第一轮真机验证使用 Android。开发与运营以尽量减少持续费用为约束。

## 2. 已确认的使用规则

| 环节 | 首版规则 |
|---|---|
| 首页 | 提供“新建报销”和“历史记录”入口。 |
| 历史记录 | 点击后进入独立页面；按创建时间组织记录；支持返回首页。 |
| 完全空白的记录 | 标题和所有项目描述均为空、没有已添加的发票或附件、没有生成结果时，再次进入历史记录自动消失；仅有默认创建时间或空白费用组也按空记录处理。空格与换行按空白处理。 |
| 报销标题 | 用户选填；默认用创建日期和时间识别记录。 |
| 费用项目 | 用户自由填写描述，内容可以是饮料、文具、打印等任意报销项目。 |
| 材料分组 | 一次报销包含多个独立费用组；编辑一组时保留其他组的内容。 |
| 完全空白的项目 | 项目描述为空或仅有空白字符，且没有发票和附件时，返回报销列表或再次打开该报销后自动移除；剩余项目按当前顺序编号。已有任意描述或材料的未完整项目继续保留。 |
| 发票 | 支持 PDF 和图片；生成前要求每组具备发票。 |
| 附件 | 统一为“付款截图／行程单（选填）”；允许添加多个材料。 |
| 添加材料 | 导入和保存原文件；点击生成后统一进行图片转换和 PDF 合成。 |
| 排版 | 每组先放发票，再放附件；PDF 保留原有页面；图片原则上一张一页。 |
| 排序 | 使用边缘拖拽手柄调整费用组顺序；组内材料支持调整顺序。 |
| 连续编辑 | 提供“保存并添加下一项”和“保存并返回列表”。当前项目完全空白时，连续添加沿用当前空白编辑位置；填写内容后再添加下一项。选择材料和临时切换后台期间保留正在编辑的项目。 |
| 生成条件 | 每组发票和描述齐全后，才可生成；已有标题、描述或材料的未完成草稿可以保存并在历史找到，完全空白记录按上述规则处理。 |
| Word 内容 | 原样保留用户描述，标明这一组对应的 PDF 起止页码。 |
| 历史再编辑 | 保存原材料、编辑信息和生成结果，支持重新打开修改和导出。 |

### 参考资料与修正规则

最初提供的样例图用于说明“发票与附件属于同一项费用”的关系。样例图展示了附件同页排版；首版采用用户后来确认的“一张图片一页”。最终输出按费用组归集材料，每组发票在前、附件在后。

| AC-02 | 第一组包含两页发票 PDF、两张附件图片；第二组只有一张发票图片。两组均填写描述后生成。 | 最终 PDF 共五页；Word 分别标明第 1—4 页、第 5 页。 | 待验证 |

## 4. 与技术设计的衔接

### 数据流程

用户导入原材料 → 按费用组保存 → 点击生成 → 合成 PDF 并统计页码 → 生成 Word → 保存结果和历史记录。

### 待验证问题

| 技术环节 | 下一阶段需要查明和验证的内容 |
|---|---|
| 聊天材料选择 | 微信提供哪些材料选择能力；怎样取得用户主动选择的图片和 PDF。 |
| 本机文件保存 | 怎样保存原材料、编辑信息和生成结果；关闭后重新打开时能否继续使用；本机保存有哪些限制。 |
| PDF 合成 | 能否在小程序中完成图片转 PDF、已有 PDF 页面合并，并按最终顺序准确统计页码。 |
| Word 生成 | 能否在小程序中生成 Word，原样保留描述，并使用对应 PDF 的实际起止页码。 |
| 手机资源限制 | Android 真机中的处理时间、内存和存储限制，以及这些限制对材料处理的影响。 |

### 现有代码搜索与筛选要求

每个技术环节开发前，由开发助手先上网搜索已有代码，比较候选方案，并记录选择理由。筛选结果写入后续技术设计与决策记录。

记录中区分“资料表明可行”和“已经在真机验证”。本文件中的产品要求用于指导实现和验收，具体技术方案由后续调研与验证确定。
